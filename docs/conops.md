# Concept of operations

**Status:** Draft for review. The [story baseline](user-stories.md) is authoritative for stakeholder intent. Agents manage execution; the system manages attention; the human manages decisions.

In the intended local workflow, an operator opens Aviary without separately starting a service; Aviary starts the local service if needed or reuses the intended running instance. The service continues after the terminal closes. This local startup and reuse workflow has been exercised; platform and operator acceptance remain open. The keyboard-operated interface offers shortcut help on demand and may show concise contextual hints, rather than a persistent full shortcut list. Its presentation uses terminal-controlled basic colors and non-color cues, with local basic-color and monochrome checks; broader accessibility and terminal acceptance remain open. V1 serves one user on a central service that listens on localhost by default, with no application authentication. The operator may explicitly select a network interface for a trusted local cluster. A future shared deployment must isolate each user’s channels and communications. Agents, using a documented CLI and portable skill, submit requests with an explanation, work context, optional supporting context, suggested answers and optionally a recommendation with its reason. The interface consolidates actionable requests and orders them by importance. The operator controls importance; agents may suggest or infer defaults from work context. The operator inspects context when needed, confirms a suggested or custom answer, or defers the request and returns to it later. A recommended answer is presented first and preselected, but no answer is sent until the operator confirms it. Completion notices identify work and results. For the normal outbound instruction, the operator enters only the text; Aviary supplies a new retry identity and targets the `all` channel as a group, with explicit confirmation before sending. A First Mate or other participant that belongs to `all` can monitor its inbox and receive the instruction; the system does not require an orchestrator or launch one. This group-addressed flow is implemented locally; the proposed shared-work queue remains a separate unresolved design. A separately addressed agent or group remains available through the communication interface; composition overrides are later scope.

In the operator workflow, a compact overview distinguishes decisions, messages and completions and indicates incomplete or unavailable data. The operator can find retained communications by text, agent or work context, browse previews, open details and return without unnecessarily losing place or an unsent draft. View and selection remain identifiable; action outcomes distinguish accepted, explicitly rejected and unknown results. Long content is readable as visible lines and survives resizing. These behaviors are implemented and locally exercised in selected scenarios; broader terminal and representative operator validation remain open.

Agents exchange messages through channels that can support one or many senders and recipients, and can address an individual or group. A V1 agent may send a targeted request to another agent and receive one correlated response, including when a requester waits or returns after restarting. Richer autonomous coordination remains subject to the later stories. Related activity references link exchanges without imposing a project hierarchy. The attention interface is a client of messaging infrastructure, not the agent execution or orchestration system.

Agents on separate machines connect to the explicitly selected network interface. Participant names are routing labels, not authenticated identities; every process that can reach the listener is trusted in V1. An accepted communication persists across service crash and restart. Identical retries with the same identity return the existing request; reuse of that identity with different content is rejected. A disconnected agent can retrieve communications accepted for it during the interruption after reconnecting; this does not promise submission to an unreachable service. The interface can close while communication continues. Operators can inspect request history and outcomes; neither automatic rollback nor cancellation of already acted-on instructions is implied.

**Validation scenarios:** Observe an operator process a mixed queue, make a one-confirmation recommended choice, investigate context, defer and recover a request, and resume interrupted work. Evaluate whether routine execution stays out of the way and whether the workflow actually reduces attention cost. Validate multi-machine recovery and access with representative participants. These user observations complement, but do not replace, requirement verification.

## Queue and interface workflow (updated 2026-11-12)

The operator browses a vertical list of decisions, messages or notices and reads the selected item's vertically arranged details in visually distinct areas. Focus distinguishes list navigation from answer selection; the interface retrieves additional data in the background and shows loading or failure without implying that a partial view is complete. Short success notifications disappear, while rejections and uncertain outcomes remain actionable. The composer shows the `all` destination and sends on an explicit action without a separate review screen. Existing keyboard and color choices are subject to usability review.

An agent lists pending decisions, possibly using API pages, and may propose a positional swap within one effective importance level. The service must prevent a stale or concurrent swap from affecting unintended items; a caller refreshes and decides what to do after a conflict. The operator's control of importance remains. Deferral keeps the decision pending, moves it to the end of its importance group and records a durable requester event; local tests cover that behavior, while broader acceptance remains open.

The operator can submit an `all` instruction while no agent is listening. The proposed shared queue retains it as outstanding until resolved, after which it is no longer in the active queue. Agents can discover and take up work; the model for individual claiming, parallel work, abandoned claims and redelivery is not yet approved. This is distinct from existing direct and group messages, whose retained recipient snapshots do not implement this queue. Whether resolved work is retained separately from the active queue, and for how long, remains open; acceptance and retry identity must not be silently weakened. No agent is launched or authenticated by this design.
