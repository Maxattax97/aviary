# Concept of operations

**Status:** Draft for review. The [story baseline](user-stories.md) is authoritative for stakeholder intent. Agents manage execution; the system manages attention; the human manages decisions.

In the intended local workflow, an operator opens Aviary without separately starting a service; Aviary starts the local service if needed or reuses the intended running instance. The service continues after the terminal closes. This is planned, not yet implemented; today the service must be started separately. The keyboard-operated interface offers shortcut help on demand and may show concise contextual hints, rather than a persistent full shortcut list. Its planned presentation uses the operator’s standardized terminal color scheme where supported and remains usable without 256 colors or color-only state cues. V1 serves one user on a central service that listens on localhost by default, with no application authentication. The operator may explicitly select a network interface for a trusted local cluster. A future shared deployment must isolate each user’s channels and communications. Agents, using a documented CLI and portable skill, submit requests with an explanation, work context, optional supporting context, suggested answers and optionally a recommendation with its reason. The interface consolidates actionable requests and orders them by importance. The operator controls importance; agents may suggest or infer defaults from work context. The operator inspects context when needed, confirms a suggested or custom answer, or defers the request and returns to it later. A recommended answer is presented first and preselected, but no answer is sent until the operator confirms it. Completion notices identify work and results. For the normal outbound instruction, the operator enters only the text; Aviary supplies a new retry identity and targets the `all` channel as a group, with explicit confirmation before sending. A First Mate or other participant that belongs to `all` can monitor its inbox and receive the instruction; the system does not require an orchestrator or launch one. This default flow is planned, not yet implemented. A separately addressed agent or group remains available through the communication interface; composition overrides are later scope.

In the planned operator workflow, a compact overview distinguishes decisions, messages and completions and indicates incomplete or unavailable data. The operator can find retained communications by text, agent or work context, browse previews, open details and return without unnecessarily losing place or an unsent draft. View and selection remain identifiable; action outcomes distinguish accepted, explicitly rejected and unknown results. Long content is readable as visible lines and survives resizing. These behaviors are targets; existing local functionality is partial and does not yet establish the complete experience.

Agents exchange messages through channels that can support one or many senders and recipients, and can address an individual or group. A V1 agent may send a targeted request to another agent and receive one correlated response, including when a requester waits or returns after restarting. Richer autonomous coordination remains subject to the later stories. Related activity references link exchanges without imposing a project hierarchy. The attention interface is a client of messaging infrastructure, not the agent execution or orchestration system.

Agents on separate machines connect to the explicitly selected network interface. Participant names are routing labels, not authenticated identities; every process that can reach the listener is trusted in V1. An accepted communication persists across service crash and restart. Identical retries with the same identity return the existing request; reuse of that identity with different content is rejected. A disconnected agent can retrieve communications accepted for it during the interruption after reconnecting; this does not promise submission to an unreachable service. The interface can close while communication continues. Operators can inspect request history and outcomes; neither automatic rollback nor cancellation of already acted-on instructions is implied.

**Validation scenarios:** Observe an operator process a mixed queue, make a one-confirmation recommended choice, investigate context, defer and recover a request, and resume interrupted work. Evaluate whether routine execution stays out of the way and whether the workflow actually reduces attention cost. Validate multi-machine recovery and access with representative participants. These user observations complement, but do not replace, requirement verification.
